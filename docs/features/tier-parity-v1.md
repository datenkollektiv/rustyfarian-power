# Feature: Tier parity v1

Adopts the tier-parity hardening contract from `rustyfarian-network` ADR-022 and `rustyfarian-ws2812` ADR-010 into this repo, as recorded in `docs/adr/003-tier-parity-contract.md`.

## Decisions
|                                                                                 Decision | Reason                                                                                                        | Rejected Alternative                          |
|-----------------------------------------------------------------------------------------:|:--------------------------------------------------------------------------------------------------------------|:----------------------------------------------|
|                                            Adopt the parity contract as an ADR, not code | The architecture already exists here; only the contract is missing                                            | Immediate code enforcement                    |
|                                                                 Document-only first wave | Naming the contract needs buy-in before code                                                                  | Building the parity compile check this wave   |
|                                             Mirror the sibling naming (`tier-parity-v1`) | Keeps cross-repo feature docs findable by the same name                                                       | A power-specific doc name                     |
|                                      Record sibling ADRs by reference, not re-litigation | The decisions were made and validated there                                                                   | Restating all sibling arguments in ADR-003    |
|                         State guarantees as observable outcomes, not identical internals | Identical internals would outlaw `BoundSleep`-style borrowing and valid timing differences                    | "Validate, block, and transition identically" |
| Classify capabilities: hardware limitation, unimplemented driver, behavioural difference | The missing esp-hal ADC/charging monitors are implementation gaps, not semantic divergence                    | One undifferentiated capability column        |
|                                             Enforce provider policy at link time as well | Duplicate or missing `critical-section` providers fail only at link (2026-10-29)                              | Compile checks alone                          |
|                       Track enforcement as committed follow-ups with acceptance criteria | An accepted contract without completion conditions is unenforceable                                           | Open-ended "potential" items                  |
|           Scope the post-rejection postcondition to observable retry and pin readability | Armed-state between rejection and retry is adapter-internal; re-binding and re-arming are tier-local concepts | A "no residue at all" postcondition           |

## Constraints
- `stoker` stays `#![no_std]` with `critical-section` as its only dependency.
- No code changes in this wave.
- Platform pins stay: ESP-IDF v5.3.3 and esp-hal `=1.2.2` in lockstep with the sibling repos.
- Tracked files may name public `rustyfarian-*` repos.

## Sleep audit: `try_sleep` post-rejection (2026-11-03)

Docs-only chunk (chunk 1); no code changed.
Findings rest on a source read of ESP-IDF v5.3.3 (`sleep_modes.c`, `sleep_gpio.c`, `rtc_sleep.c` per chip) and esp-hal 1.2.2, plus both adapters' code.

### Side-by-side comparison

| Aspect                 | ESP-IDF (`esp_sleep.rs`)                                                                                                                                                                                                                                                                                                                       | esp-hal (`sleep.rs`)                                                                                                                                                                                                                                                                                       |
|:-----------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Validation order       | Shared `validate_wake_sources` first, then the per-chip mask check and the `isolate_gpio` conflict, all before the first SDK call; a `Config` error leaves the wake configuration untouched                                                                                                                                                    | Same shared validator first in `plan()`, plus the hal-only checks (`PinNotBound`, the `MIN_TIMER_MS` floor, deadline overflow); the hardware-state checks (foreign pins, UART drain) run read-only first inside the critical section; every error before arming leaves everything untouched                |
| Rejection detection    | EXT1 chips and the S3 rely on the hardware reject of `esp_deep_sleep_try_to_start`; C2/C3 hardware does not reject a held GPIO wake pin, so the tier reads the wake pins itself right before entry and returns the same `Rejected` shape                                                                                                       | `sleep_deep_with_rejection` inside one critical section with arming and cleanup; no software pre-read                                                                                                                                                                                                      |
| State after `Rejected` | Wake sources, timer target and isolation config stay applied; a hardware rejection also leaves the wake pins held (RTC route + pad hold on EXT1 chips, `gpio_hold_en` + internal pull on C2/C3), because the prepare hooks run before the reject decision; the C2/C3 pre-read reject holds nothing; a retry re-runs `configure()` from scratch | `disarm()` before returning: every bound pin is unlistened, cleared and reset to the default `WakeupConfig`, the deadline cleared; non-wake pads isolated at entry (S3 GPIO22+) are not restored; a retry re-arms from scratch                                                                             |
| Timer limits           | `MAX_TIMER_MS` from `stoker` (`u32::MAX` ms, ~49.7 days); no floor                                                                                                                                                                                                                                                                             | Same `MAX_TIMER_MS`, plus the provisional `MIN_TIMER_MS = 1` floor and the `POST_ARM_MARGIN_US` post-arm guard, because esp-hal writes a 48-bit comparator and `sleep_deep_with_rejection` has no deadline assert (ADR-001 § 4c); the floor is a documented platform exception pending `short-timer-sweep` |
| Wake-cause capture     | `EspWakeCauseSource` reads the registers live; the EXT1 status is documented as preserved until the next sleep entry — whether a rejected attempt counts as an entry is unverified (open question below)                                                                                                                                       | `EspHalWakeCauseSource::capture` must run at boot before the first `try_sleep`: a rejected sleep ends in `record_wakeup()` and overwrites the per-pin wake record                                                                                                                                          |

### The three IDF rejection paths

- EXT1 chips (ESP32, S3, C6): the hardware reject fires after `ext1_wakeup_prepare`, so a rejected attempt still leaves the masked pins RTC-routed and RTC-held, the stale `ext1_rtc_gpio_mask` (not cleared by `esp_sleep_disable_wakeup_source(ALL)`), and the timer/isolation config applied.
- C2/C3 hardware reject (timer-only, or a pin that reached its level after the pre-read): wake pins keep their `gpio_hold_en` hold and the internal pull applied at entry; per-pin wake enables and the SDK's `gpio_wakeup_mask` (no public clear in IDF v5.3.3) survive.
- C2/C3 software pre-read reject (`gpio_wake_pins_asserted`): no sleep entry happened, so the residue is configuration only and no pin is held — this path already satisfies the postcondition.

### Decided postcondition (now ADR-003 point 1)

After any `Rejected` attempt the caller may retry immediately through the same trait object — no recovery, re-construction, or pin re-binding step — and the retry is observably a fresh attempt: the same validation outcomes and error kinds apply, and a `Timer` duration counts from the retry.
Every wake pin named in the rejected request's `pin_mask` is usable as a plain digital input once the call has returned (on the esp-hal tier, once the `BoundSleep` borrow ends).
Whether wake sources stay armed between rejection and retry is adapter-internal, not an observable.
Out of scope: the isolation state of non-wake pads, timer-deadline persistence, and the C2/C3 within-boot GPIO-wake residue (the unclearable SDK mask and the I6 pull fight, both reset-cleared and already documented).

### Why no chip needs a weaker postcondition

All three IDF rejection paths can meet the postcondition in software; the esp-hal tier already meets it for bound pins.
Bench H1-level on the S3 (2026-10-14, 675+ consecutive `Rejected` at 50 ms) shows the full re-configure retry is stable and idempotent today.
Holds do not block `gpio_get_level` (hold freezes pad configuration latches, not the input amplifier), so the readability clause is bench-unverified rather than hardware-blocked; the adapter change releases the holds regardless, so reconfiguration for other use also works without a documented `gpio_hold_dis` caveat.

### Latent bug found by the audit

A retry that changes the EXT1 pin/level combination can fail with `ESP_ERR_NOT_ALLOWED` in the mask merge (`sleep_modes.c:1791-1810`), because the disable-all branch does not clear `s_config.ext1_rtc_gpio_mask` (`sleep_modes.c:1544-1559`).
Same-pin/same-level retries (the benched case) are unaffected.
The `esp_sleep_disable_ext1_wakeup_io(0)` call in the adapter-change follow-up closes it.
